# 两个 DSH 插件：让智能体学会交接和清理

DSH（DeepSeek Harness）是一个编码智能体宿主：它把模型、工具、会话记忆组装在一起，让 AI 能在真实项目里长期干活。它能装插件，装上就能给 AI 加新工具。

这里介绍两个插件，解决的是同一类问题的两个不同侧面——**一个会话开久了，怎么继续往下走**。

- `new_work`：把活交接给一个新会话，换个人、换副立场继续。
- `compact`：让 AI 自己判断"前面这些没用了"，主动清理上下文。

两个都是独立插件，可以分开装，也可以一起装。

## 仓库结构

```
dsh-toolkit/
├── dsh-tool-handoff-session/   # 提供 new_work 工具
└── dsh-tool-compact/           # 提供 compact 工具
```

每个目录都有自己的 README（实现说明）和 CHANGELOG（改动历史），根目录这份讲的是"为什么要做这两个东西"。

## 一、`new_work`：换身份接着干

### 问题

一个会话开久了，会遇到两件事：

1. 上下文被早期过程占满。真正重要的只有几条结论，剩下的都是"我当时怎么试的"。
2. 事情本身变了。一开始是商量方案，后来要动手写代码；一开始是研究工作区，后来要改自己的配置。同一副立场处理不同的活，容易拧巴。

### 做法

给 AI 一个工具。它在当前对话的最后一步调用，做三件事：

1. 把该交代的写下来：干到哪了、下一步第一件事是什么、有哪些坑、还欠用户什么。
2. 在指定目录开一个新会话。
3. 把这段内容作为新会话的第一条消息送进去。

### 一个关键的设计选择

**不让新会话知道自己是"被转交"的。**

第一版和第二版都在正文里解释"这段文字是谁写的、你不该把它当成什么"，结果新会话的注意力全被引到那份材料上，第一句常常变成对交接本身的评点。

现在的正文只有两块，中间不插一个字的说明：本会话最后一段发言的原文，接上留下的记录。读起来就是同一段思路在往下走。

要让新会话感觉自己就是老对话自然延续下来的，而不是由别人拉起来的。

### 三档力度

换身份不等于每次都要兴师动众，所以分成三档：

| 力度 | 做什么 | 什么时候用 |
| --- | --- | --- |
| 加载技能 | 会话不动，只是多一套做事规矩 | 要写代码、要排版本、要讲解，规矩就够 |
| 换状态 | 同一目录开新会话，换一种干活的劲头 | 活还是那件活，只是要沉下心较真了 |
| 换身份 | 换一个目录开新会话，读另一份说明文件 | 面对的事情变了，该由另一个身份来做 |

前两档便宜，第三档会丢掉当前上下文，所以要判断清楚。

### 还有一条：交接即暂停

工具描述里写死了四条规矩：

1. 只在对话最后一步调用；调用之后这一轮不再分析、总结、规划，也不动文件。
2. 调用之前，把还欠用户的全部写进交接内容。
3. 调用成功之后，这一轮的回复里不许再留问题或待办。
4. 交接之后不跟新会话并行干活：不回头读它的日志、不等它汇报。

理由很直白：交接之后焦点转到新会话，在这边再问也没人答；回头去读、去等，等于把"交班"干成了"派侦察兵回来汇报"，活还是自己在干，新会话也失去了主人位置。

## 二、`compact`：自己判断该清理了

### 问题

DSH 自带的上下文压缩只有三条触发路径，没有一条由模型决定：

- **长度阈值**：每次请求前量一次，越过窗口的某个比例才压。
- **上下文溢出**：模型报错说装不下了，强行压一次。
- **手动命令**：用户自己敲命令，且只在空闲时可用。

问题在于，**真正该清理的时刻往往不是"快装满了"**。比如刚读完一个几百行的文件、结论已经摘出来了，原文留着占地方，但还没到装不下的程度，宿主就不会动。

### 做法

给 AI 一个工具。它判断得出"前面的上下文对接下来要做的事已经没用了"，就提交一次压缩。

### 为什么是"提交"，不是"立刻压"

工具是在助手回合**中间**执行的，那时会话还占着。压缩服务有两个入口：一个要求回合在进行中，能立刻压；一个要求会话空闲。

一开始走的是"立刻压"，但那样模型会在压完之后才继续说话，压缩的收益要等下一轮才体现，白白让这一轮卡住等一次摘要请求。

改成登记任务后：

- 模型调用工具时零等待，本轮照常说完；
- 真正压缩在会话空下来的那一刻发生；
- 压缩期间用户发的新消息按原有顺序排队，等压缩落地后才开始，不会丢也不会乱序。

代价是结果没法回流给模型——那一轮已经结束了。这是这个设计必须付的账。

### 一个反直觉的发现

**光给工具，模型不会用。**

LangChain 的 Deep Agents 团队做过同样的事：注册一个模型可调用的压缩工具，并在系统提示里给「值得压的时机」清单。实测结果很保守，基准里一次都没触发。

所以时机清单必须写到位，而且直接写进工具描述——工具描述本身就是模型可见的提示词，不用改系统提示。

现在写进去的五条时机：

- 一段任务收尾干净、结论已定，推导过程用不到了；
- 刚读完大量材料并提炼出结论；
- 接下来要吞进大量新内容，先把旧的压掉；
- 即将进入一条很长的流程；
- 原先的结论被推翻，旧上下文只会误导。

以及三条不该提交的：

- 还在连续任务中间，前因后果马上要用；
- 还需要引用早期原文，但还没摘出来；
- 没有需要留存的结论：不必为了压缩而压缩。

### 一切压缩逻辑都复用宿主

插件不碰摘要提示词、不碰保留范围的算法、不写会话记录。它只做两件事：挑对时机，处理失败。

失败处理有个细节：压缩只在真空闲时能启动，撞上别的维护任务会报"忙"，这类失败多半是瞬时的，所以保留任务等下次空闲重试，最多三次；没有可压缩的内容时安静结束，不重试。

## 怎么装

两个插件都是 DSH 的宿主插件，装法一样。

1. 把仓库 clone 到本机任意位置：

   ```
   git clone <本仓库地址> dsh-toolkit
   ```

2. 在你使用的 profile 的 `package.json` 里加一条本地链接依赖。`link:` 后面换成你 clone 下来的实际位置：

   ```json
   "dependencies": {
     "dsh-tool-handoff-session": "link:../../dsh-toolkit/dsh-tool-handoff-session",
     "dsh-tool-compact": "link:../../dsh-toolkit/dsh-tool-compact"
   }
   ```

3. 在同一个文件的 `dsh.profile.bundles` 列表里加上要装的插件名：

   ```json
   "dsh": {
     "profile": {
       "bundles": ["dsh-tool-handoff-session", "dsh-tool-compact"]
     }
   }
   ```

4. 装依赖，重启宿主。

`bundles` 是启动时读的，热重载改不到，所以这一步必须重启。

## 为什么值得单独做成插件

这两件事其实都可以写进宿主本体，但做成插件有三个好处：

- 不动本体，宿主升级时不会被冲掉；
- 能单独关掉，出问题时影响面只有插件本身；
- 能被别人改。你觉得时机清单该加一条，改工具描述就行，不用等上游发版。

## 已知限制

`new_work`：

- 模型接口上的角色只有 user / assistant / tool 三种，改不了。交接内容在会话记录里仍然是 user 角色，插件能控制的只有来源标记和正文措辞，"不留痕迹"只能做到正文层面。

`compact`：

- 压缩发生在回合之后，模型无法在同一轮里得知压了多少。
- 摘要格式由压缩后端决定，插件不干预。
